# v3.0指示書に基づく改修計画

2026-11-12。今回の成果は監査・比較・技術設計。v0.4.0の挙動を保護し、大規模改修前の基準を固定した。資料不足の秒数を確定するための承認待ちは設けず、証拠取得と独立した基盤改善を先行できる。

## 最初の3項目

|順|改修|理由/影響|受入条件|
|---|---|---|---|
|1|設備ID、台別在庫、配膳Task/料理予約|見かけ2台・実質1台を解消。data/cafe、Cafe、Scene/UIの在庫参照に影響|2台・2人・残り1食で一度だけ提供。退店/感染/休憩/期限切れで保存則成立|
|2|経路/作業点予約、取消、閉塞復帰|新しい台で集中と行き詰まりが増える。movement/grid/Cafeに影響|対向狭路・完全封鎖・途中取消で瞬間移動/永久待機なし。レイアウト変更の経路更新|
|3|時間設定とnormal/playtest|現在の短縮値を原作扱いしない。Cafe/Scene/UI/テストに影響|まず同値抽出で全回帰維持。既知レシピのみ出典付き通常値。表示と実時間一致|

各項目は別コミット/PRにする。最初のコミットは設備IDと互換adapterだけで挙動を維持。次に在庫保存則の失敗テスト、台別Batchと予約を実装。旧API stock/stockOf/orderは移行中の読取adapterとして残し、単体HTML生成の動線を保つ。

## 後続段階

4. キャラクター状態と演技の同期。pickup/cooking/cleaning/rest/outburstを開始・途中・終了に分け、表情を状態別にする。食器visualId共通化。固定視点/同人数/同配置で比較。足元追跡と複数fps録画。
5. selectedActorIdとpaneを分離。家具IDからタップ領域生成。ピンチ/セーフエリア、iPhone実機確認。選択継続・キャンセル・ドラッグ誤作動を回帰。
6. 家具編集→購入/拡張→バージョン付き保存→PWA→NPC襲撃。戦闘は店内暴走から分離。未実装UIを実行可能に見せない。

## 実現可能性・リスク

TypeScript純粋シミュレーションと既存A*を再利用可能。小さい店舗では全候補の経路比較で始め、layoutRevision単位の静的経路cacheを導入する。動的占有はcacheしない。Phaser描画の書換えは不要。

最大の移行リスクはグローバル座標定数と配列index依存。家具ID移行前に自由配置UIを追加しない。予約はUIから直接書き換えずCafeコマンド経由。原作タイミング未確認は機能設計と切り離す。短縮モードと通常モードの経済差はセーブ互換で明示する。

完了判断: テスト合格だけで再現度達成とはしない。原作観測、同構図比較、実機操作を別々に報告。参考画像を含む比較資料は公開GitHubへ追加しない。
